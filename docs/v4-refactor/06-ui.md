# UI 重写：只读投影渲染 + 多 session 分屏（实施设计）

> **状态：V4 UI 主链路与跨 workspace workbench 已落地；正文保留实施期设计和容量目标。**
> 当前入口是 `packages/ui/src/v4/SessionPane.tsx`、`sessionDataLayer.ts`、
> `conversationProjectionStore.ts`、`paneLayoutStore.ts`、`workspaceConnectionRegistry.ts` 和
> `V4WorkspaceChatArea.tsx`。下文“现状病根”“分步落地”“可删行数”是迁移轨迹，不是当前代码描述。

## 当前落地结果（2026-07-15）

- conversation rows、phase、actions、queue、interaction 和 config 由 per-session projection store 只读消费；
  snapshot 原子替换、delta 连续 apply、gap/epoch 触发 recovery。
- `SessionDataLayer` 按 topic 复用 store 并用 lease/refCount 管订阅；pane 关闭只释放视图，不停止 CLI session。
- pane layout 已使用树模型，支持 draft pane、session pane、split、focused pane 和 renderer workbench 恢复。
- `workspaceConnectionRegistry` 按 endpoint/workspace scope 复用连接，远程 pane 使用自己的 Host/service，
  不把相同 workspacePath 当作相同 identity。
- task/session 列表活性读取 sessions-index；pin/archive/group/unread 从 tasks-index join。
- `zcodeSessionStore` 仍保留 shell/navigation/task-list/兼容 metadata；“conversation zustand 全删”只表示
  删除它对 conversation 事实的所有权，不表示物理删除整个 store。

## 实施期 projection store 设计

> 2026-07-13 侧栏状态所有权补充：这里的“conversation 相关 zustand 全删”只指 conversation 业务事实，不是移除 Zustand 库或所有 renderer-local store。`activeTaskId`、导航、草稿、滚动/focus 等本地 UI 状态继续使用 Zustand；侧栏的 phase/activity/attention 改读 sessions-index，pin/archive/group/unread 改读 tasks-index field join，禁止再读旧 runtime/ui/unread/taskListCache 事实表。详见 [V4 左侧任务状态权威收敛设计](../superpowers/specs/2026-07-13-v4-sidebar-task-state-authority-design.md)。

> 2026-07-13 启动/入口语义补充：app 冷启动和 workspace-only 打开一律进入草稿，不消费 pane last-session，也不激活持久 workbench group/pane；只有同一 renderer reload 的首个 workspace 可以恢复刷新前的可见 session，保留输出中续流。所有 desktop workspace/new-task 入口必须共用“精确激活 workspace → 退出 active workbench group → reset primary pane → startDraft”的导航事务；显式 session/task 导航随后以目标 `sessionId` 覆盖草稿。手机 `/remote` 不消费 desktop group/pane 持久化，replayable 恢复边界不变。完整边界见 [Workspace / App 入口草稿态](../workspace-entry-draft.md)。

conversation 相关 zustand 全删（`packages/ui/src/store/zcodeSessionStore*` 约 5000 行）。替代物是很薄的 per-session projection store：

```text
Map<sessionId, { projection, optimisticOverlay }>
  - 唯一写入方: 订阅推送 (snapshot 整体替换 / row patch / seq 连续 apply)
  - UI 只读
本地态 (与 projection 物理分开存):
  draft / scroll / focus / hover / 面板开合
  draft 与在途 commandId 持久到 localStorage
```

右侧 side pane 的 `tabs` 是 workspace 级 renderer-local registry；但面板的展开/收起是
对话级显示偏好，按 `workspaceKey + sidePaneOwnerId` 保存。切换对话时，已有可见 tab 不能
覆盖用户对当前对话的主动收起；只有用户点击打开/激活新的 side pane 内容，或点击顶部切换
按钮主动展开，才更新该对话的展开偏好。没有可见 tab 时仍强制收起。该偏好不进入 Host、Agent、
session snapshot 或 remote replayable 数据。

客户端遵守 [04-sync-and-recovery.md](./04-sync-and-recovery.md) 的三条规则；除 optimistic overlay（pending/stopping 展示）外不产生任何 conversation 事实。UI 端自行推导控制 flag 的代码全部作废（`useChatViewDisplayFlags.ts`、`lib/chatStatus.ts` 等），改由 projection 的 sessionControl/actionAvailability 直接驱动。

## 分屏：三层状态分离 + SessionPane 实例化

现状病根：三件事焊死在一起——`tabStore.activeTabId` 单值既是「显示什么」又是「操作谁」，store 按 workspace 分桶但消费端全局取「当前」，`ChatView` 是单例。重写为三层单向依赖的状态：

```text
① SessionDataLayer —— 纯数据，不知道「显示」这回事
   Map<sessionKey, SessionStore>          sessionKey = workspace + sessionId
   SessionStore = { projection, optimisticOverlay, 订阅句柄, refCount }
   唯一写入方: 订阅推送。生命周期 = 引用计数:
   有 pane 引用 → 订阅; 归零 → 延迟退订 (keep-warm ~30s, 防拖拽抖动)

② LayoutLayer —— 布局，不知道 session 内容
   panes: [{ paneId, sessionKey | null, size }]   (一维分栏 1-4 pane 起步,
   持久化 → 刷新后恢复整个多屏工作台              模型留成可扩展成树)

③ FocusLayer —— 交互路由
   focusedPaneId 单值 (全应用唯一的「当前」就剩这一个)
   全局快捷键 (stop/发送/切 pane) 一律路由到 focused pane
```

Focus 指向 Layout 的 pane，pane 指向 Data 的 sessionKey，Data 对上两层零感知。**任何组件禁止读「全局当前 session」——这个概念不存在**，只有「我这个 pane 绑定的 session」。

```text
<SessionPane paneId sessionKey>          组件树内部经 SessionPaneContext 取数
  ├── PaneHeader   (标题/状态点/关闭·拆分)
  ├── Timeline     (虚拟滚动, 吃 store.rows, row 级 memo)
  ├── QueuePanel   (吃 projection.queue)
  └── Composer     (吃 projection.inputRouting + actionAvailability)
```

pane 之间唯一共享的是 SessionDataLayer 和底下那一条连接（按 topic 多路复用，不是每 pane 一条）。新开 pane 就是一次 `subscribe(base=none)`，与刷新、新设备是同一路径。

### 本地 UI 态的归属

| 状态 | key | 理由 |
| --- | --- | --- |
| 滚动位置、折叠状态、跟随底部开关 | paneId | 两个 pane 看同一 session 的不同位置 |
| composer 草稿、附件暂存 | sessionKey | 草稿属于「我要对这个 session 说什么」，换 pane 不丢 |
| side pane tabs | workspaceKey | Browser/Git/Preview tab 属于同一工作区的辅助工作区，切换对话不销毁 tab |
| side pane 展开/收起偏好 | workspaceKey + sidePaneOwnerId | 用户主动收起某个对话的 side pane 后，回到该对话仍保持收起 |

### 分屏规则

1. **允许同一 session 出现在多个 pane**：store 共享、readonly，第二个 pane 只是多一个视图（一边看历史一边看新输出）。
2. **关 pane ≠ 停 session**：pane 关闭只是退订视图，session 在 CLI 里照跑——与「web 页面关了 CLI 继续跑」同一条总原则。
3. **不可见 session 的活动感知走轻量通道**：侧栏 phase/状态点/permission/userInput attention 订阅 conflated 的 sessions-index 摘要（最新态、天然有界），不为一个状态标记订阅全量 rows；未读 `unreadAt` 属于 tasks-index membership，不从 activity time 推导。
4. **stop 等危险操作永远作用于明确的 pane**：快捷键走 focused pane，按钮走自己所在 pane，无「作用于当前 session」的模糊语义。

### 可见性 QoS

订阅带 visibility hint（`foreground / background`），CLI 每订阅者 flush buffer 据此分级：焦点 pane 最小合批窗口、最高 drain 优先级；非焦点 pane 更大合批窗口；侧栏摘要只发 sessionControl conflation。不是新机制——pane 可见性只是已有优先级调度（[05-transport-and-backpressure.md](./05-transport-and-backpressure.md)）的一个输入。

### 边界决策

- **空 pane / 新会话**：pane 允许绑 `null`，显示新会话 composer；首次发送创建 session 后原地绑定（对应协议 `draft` phase）。
- **跨 workspace 分屏**：一期只做同 workspace 内。sessionKey 已含 workspace、数据模型天然支持，但跨 workspace 需要 UI shell 持多条 host 连接（`Map<workspaceKey, Connection>`），作为分屏二期。二期方案已规划为「多 pane 跨 workspace 工作台」（二叉分割树 1–4 pane + `workspaceConnectionRegistry` 按 `endpointKey + workspaceKey` 复用连接），设计 spec 见 [v4-split-pane-workbench.md](../v4-split-pane-workbench.md)。

### 分步落地与验收

1. 数据层先行：SessionDataLayer + 引用计数订阅，先用单 pane 跑通（即「新 store 替换旧 zustand」本身）；
2. 双 pane 最小分屏：LayoutLayer + FocusLayer + SessionPane 实例化；
3. 打磨：1–4 pane 布局操作、visibility QoS、同 session 双 pane、空 pane 动线。

性能验收基线：**4 个 pane 同时流式输出，交互不掉帧**。配套 e2e：双 pane 各自流式互不干扰；pane A 点 stop 只停 A 绑定的 session；刷新后布局 + 各 pane 内容 + 水位全恢复；同 session 双 pane 内容严格一致、滚动互独立。

## 渲染：虚拟滚动 + row 级更新

- 消息列表上 `@tanstack/react-virtual`（仓库已有依赖；`GitPane.tsx`、workspace-grouped-tasks 有参考实现）。现聊天区零虚拟化，全量 `map` 渲染靠 `content-visibility: auto` 兜底（`ChatConversationContent.tsx:41`）。
- 虚拟化的度量单位就是 projection 的 `rows[]`——rows 在 CLI 算好、有稳定 key，客户端不再每帧重算 turn 分组（现 `buildChatMessageTurnGroups` + 三层 memo 补丁链作废）。
- 流式更新只 patch 对应 row，配合 row 级 memo，多 pane 同时流式互不牵连。
- **row 级订阅**：组件按 rowId 订阅自己的行（selector 粒度 = 行），列表容器只订阅 rows 的长度/窗口变化。
- **客户端不做第二层消息合并**：合并点唯一在服务端 flush（[05](./05-transport-and-backpressure.md) 频率预算链），客户端拿帧即 apply，最多 rAF 对齐渲染节拍。
- **长文本 row 的 markdown 重解析是认领的渲染热点**：流式 row 每 30ms 追加一次，不能每次全量重跑 markdown parse——用流式增量解析/仅尾部块重渲（`packages/stream-animate` 为现成落点）；屏外 row 不渲染兜底。此项与虚拟滚动并列为渲染层第二个性能验收项。
